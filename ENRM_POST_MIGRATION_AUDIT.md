## Scope and evidence limits

This was a read-only review. No source code, production data, DNS, Cloudflare deployment settings, or hosted Supabase settings were changed. No request was sent to the production website or production Supabase. HTTP checks were made against the locally built OpenNext Worker with Wrangler `dev --local`.

The local Worker received only `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` from its local environment. The Next.js code reads `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY`, so the local checks used the checked-in static catalogue rather than a live Supabase dataset. Consequently, live publication rules, image uploads from Supabase Storage, hosted authentication, RLS behavior, real order submission, and live product metadata were not runtime-tested. The Cloudflare dashboard was not inspected.

The checked-in product record used for a representative local product route was **ENRM-HM-031**, Liqui Moly Longtime High Tech 5W-30, 5 L. This is a real record in `public/catalogue.json`; it is not asserted to be a currently published hosted record. A browser tab could not be opened to the local Worker because the computer-use browser capability returned `Capability is not available: visibility`. Lighthouse, Playwright, and Puppeteer are not installed in the project, so no browser-based performance score or visual QA is claimed.

Root metadata sets a generic Twitter summary-large-image card without an image. Cart and checkout are correctly noindex, but inherit the generic social metadata. The product path constructs metadata image URLs by prefixing `/` to `product.recto`; this breaks values that are already absolute Supabase Storage URLs.

`NEXT_PUBLIC_SITE_URL` defaults to `https://enrm.ma`. That is the intended domain, but production DNS/TLS and Cloudflare environment configuration were not checked. There is no preview/staging `noindex` or access-control rule in the application. A temporary Worker hostname can therefore serve publicly crawlable pages; static pages have no canonical and may be indexed under that hostname. Set an explicit per-environment site URL and prevent staging indexation before exposing a preview.

The sitemap is technically well-formed and excludes nonpublic routes. Google may crawl these routes, but an XML sitemap is only a discovery hint and does not prove indexing. Search Console was not inspected, so current Google index state is **unknown**. See [Google’s sitemap guidance](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap) and [canonicalization guidance](https://developers.google.com/search/docs/crawling-indexing/canonicalization).

The Product JSON-LD is syntactically valid but is not a full commerce Offer. This matches the website’s “indicative price, availability to confirm” manual order-request workflow and avoids representing a provisional price as a guaranteed offer. Google’s Product snippet requirements use Offer, Review, or AggregateRating fields for eligibility; no rating/review claims should be added. See [Google’s Product snippet documentation](https://developers.google.com/search/docs/appearance/structured-data/product-snippet).

## Images and performance evidence

- `src/lib/legacy-render.ts` and `CartClient.tsx` build image URLs with raw `<img>` elements. They set some fixed dimensions and lazy-load cards/related items, but do not use responsive `srcset` or Next’s image component.
- `next.config.ts` declares AVIF/WebP formats, but that alone does not make raw `<img>` output optimized. The actual local `/_next/image` response for the sampled 5 L product stayed PNG at the original 435,387 bytes for width 384/q75; width 256 and quality 20 were rejected, and Wrangler warned that the `IMAGES` binding is undefined. No transformed output was demonstrated.
- The sample correct 5 L variant rendered its own 5 L image, with exact SKU and useful alt text. All 174 nonempty local catalogue image paths resolve to files. Empty image fields render placeholders; full visual inspection of those fallbacks was not performed.
- The admin upload validates JPEG/PNG/WebP and client size ≤1 MiB; the bucket migration also restricts MIME and size. However, upload code saves the absolute URL returned by Supabase Storage while storefront rendering prefixes `/` as if every image were a local path. A newly uploaded product image can therefore produce a malformed path on the storefront, cart, Open Graph metadata, and JSON-LD. Existing hosted values were not inspected.
- Largest sampled local assets by file size include a 16,688,138-byte `driving.mp4`, a 10,629,754-byte homepage `hero-oil.mp4`, and a 2,096,225-byte product PNG. The homepage video uses `preload="metadata"`; existing motion code pauses videos when offscreen/hidden and respects reduced motion. Actual network transfer, LCP impact, and mobile data use were not measured.
- Cart and checkout serialize the full 210-product catalogue into their client components; local decoded HTML bodies were ~223 KB for each. This is avoidable because those pages need only products already in the cart.
- No measured LCP, INP, CLS, TBT, image transfer totals, JavaScript route transfer, or field data is available. Do not describe the site as “Core Web Vitals passed.”

### Authentication and database observations

The administration HTML shell and JavaScript can be fetched without logging in. In the checked response, the shell contained no order/customer records. Authenticated admin data is fetched from Supabase from the browser; actual protection must come from database RLS and the role-checked RPCs, not the route’s initial HTTP response. `profiles.role` is not editable by an ordinary authenticated user under the reviewed grants. The public `is_enrm_admin()` helper only returns whether the caller is an admin; it does not return profile data.

The SQL review found consistent `search_path = ''` on the reviewed `SECURITY DEFINER` functions and schema-qualified table access. The order function’s design handles repeated request IDs and serializes inventory-row updates before checking/decrementing stock. This is favorable static evidence, not a live proof. Supabase’s own guidance calls for allow/deny tests for anon and authenticated roles; no `supabase/tests/` SQL policy suite exists in this repository and the local Supabase status command did not provide a running test stack. No disposable non-admin/admin users were used.

The SSR helper at `src/lib/supabase/server.ts` does not protect `/admin`; it is not imported by any route, and no `proxy.ts` or middleware refreshes/verifies a server session. This is not presently evidence of an RLS bypass because the app does not server-render private order data, but server-side route protection and session refresh are not implemented. Supabase’s current Next.js SSR guidance calls for a proxy to refresh cookies and verified claims before trusting a session; see [Supabase SSR client guidance](https://supabase.com/docs/guides/auth/server-side/creating-a-client?framework=nextjs&queryGroups=framework&router=pages) and [RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security).

No customer or order data was accessed during this audit. No public order was created, no stock was changed, and no upload was attempted.

## Server Actions, APIs, and database security

- No Next Route Handler, Server Action, or separate API backend was found. The storefront checkout uses the browser Supabase client and calls `place_enrm_order` directly.
- The order RPC is the only intended unauthenticated data mutation: it creates an order request. The function derives price and product snapshots from database rows, validates inputs, protects against duplicate request IDs, checks and locks inventory, and creates order plus items in a transaction.
- Admin order updates go through `update_enrm_order`, which requires `is_enrm_admin()`, bounds tracking/note lengths, locks the order row, prevents reactivation after cancellation, restores reserved stock only on the first cancellation, and updates the order.
- Public table privileges and RLS in the migrations restrict order, item, inventory, and history access. The live deployed database may differ from these repository migrations; that state was not inspected.
- Public RPC abuse throttling/Turnstile is absent after the request-limit migration was removed. This allows automation to consume database work or create nuisance orders; assess a Cloudflare edge challenge or IP-based throttle that does not impose a per-phone order cap.
- File type/size validation is in the UI and Supabase bucket policy. Test server-side rejection with an admin staging account; browser validation alone is bypassable.
- No service-role key was found. Error strings from Supabase are shown in admin UI in some flows; verify they do not include sensitive internal details in staging.
- The local Worker response did not include Content-Security-Policy, Strict-Transport-Security, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, or Permissions-Policy. Production Cloudflare edge rules may add some of these, but were not inspected. Configure and verify a suitable response-header policy at the layer that owns production traffic.

For Cloudflare OpenNext, the built Worker served this local route set successfully, but a local Worker run does not prove production bindings, custom-domain DNS/TLS, or production asset/image behavior. The OpenNext adapter currently documents image optimization via Cloudflare Images; ENRM does not use `next/image` in the sampled page output or demonstrate a Cloudflare Images binding/configuration. See [Cloudflare OpenNext documentation](https://developers.cloudflare.com/workers/framework-guides/web-apps/opennext/).

## Critical Fixes Before Production

### P0 — Configure and prove Next.js Supabase variables in a staging Worker

- **Evidence:** `src/lib/catalogue.ts` gates Supabase access on `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY`. Local Wrangler showed only `VITE_*` variables. With the new build and old names, the site silently uses `public/catalogue.json`, `hasSupabaseConfig` is false, checkout refuses to create a real request, and admin can use demo fallback.
- **Remediation:** set the `NEXT_PUBLIC_*` variables and `NEXT_PUBLIC_SITE_URL` in a non-production Cloudflare preview/staging environment, with only the anon key (never service-role). Verify server-rendered rows come from staging and that no demo fallback is shown.
- **Acceptance:** staging response shows a known staging-only catalogue change; an order request appears once with database-derived price and stock handling; admin can read/update it; public anon cannot read it; no service-role string is in emitted assets.

### P0 — Run an authorization matrix against isolated Supabase data

- **Evidence:** migrations appear restrictive, but no live/local database test stack or `supabase/tests/` RLS suite is available. Hosted policy state was not read.
- **Remediation:** create disposable anon, customer, and admin test identities in staging and test direct PostgREST/Storage/RPC calls, not only the UI.
- **Acceptance:** anon/customer cannot select orders/items/inventory/status history, mutate products/categories/inventory, upload/delete media, or update an order; admin can perform intended actions; anon can only submit a valid order request; duplicate request ID returns the original request and concurrent requests cannot oversell; customer A cannot read customer B/order data.

### P1 — Repair Supabase Storage image URL handling

- **Evidence:** `src/admin/main.ts` saves `getPublicUrl(...).data.publicUrl` as an absolute `recto` URL. `src/lib/legacy-render.ts`, product metadata, and `CartClient.tsx` prepend `/` to that value as if it were a local path.
- **Remediation:** use one URL resolver that preserves absolute HTTPS Storage URLs and safely resolves local asset paths, and use it for cards, details, cart, OG/Twitter metadata, and JSON-LD.
- **Acceptance:** upload a disposable 5 L product image in staging; all listed surfaces return 200 and show the same exact SKU image; the 1 L variant remains distinct.

### P1 — Complete per-route SEO and preview-indexing controls

- **Evidence:** root metadata has no canonical or OG image; static pages inherit a generic Open Graph/Twitter title; most static routes lack canonical links; no staging-only `noindex` or access restriction exists; local robots disallows admin even though it also emits noindex.
- **Remediation:** add meaningful page-specific Open Graph/Twitter metadata, an image, and canonicals for indexable public pages; configure production site URL explicitly and protect/noindex staging without blocking crawlers from reading a noindex directive.
- **Acceptance:** inspect raw response HTML on staging and production hostname; each indexable route has one correct self-canonical and relevant title/description/social tags; all staging routes are non-indexable; cart/checkout/admin remain excluded.

### P1 — Decide and deploy non-phone-based public RPC abuse protection

- **Evidence:** `place_enrm_order` is anonymously executable by design; migration `20261107000700_remove_unrequested_request_limits.sql` removes the request-limit table/wrapper; no Turnstile or edge throttle was found.
- **Remediation:** evaluate Cloudflare challenge or IP/edge rate controls that protect infrastructure without imposing a fixed order-per-phone limit. Keep server/database validation authoritative.
- **Acceptance:** automated burst/spam tests from staging are rejected or throttled, legitimate repeated customer orders remain possible, and no private order data is exposed.

### P1 — Add and verify runtime security headers

- **Evidence:** local Worker HTML responses contain none of CSP, HSTS, frame protection, nosniff, Referrer-Policy, or Permissions-Policy, and no project config declares them. Production edge behavior is unknown.
- **Remediation:** choose a compatible header set at Cloudflare or app layer; test inline legacy scripts and Next JSON-LD against CSP before enforcing it.
- **Acceptance:** staging HTTPS responses include the approved policy, with no mixed content, clickjacking, script failures, or login regressions.

### P1 — Make server-side auth and session verification explicit for protected server routes

- **Evidence:** `/admin` returns a public shell with HTTP 200; login and role checks happen in browser JavaScript. `src/lib/supabase/server.ts` is unused; no `proxy.ts`/middleware refreshes sessions or verifies claims. Current private data is fetched from Supabase directly and relies on RLS.
- **Remediation:** before adding any server-rendered admin data or Server Actions, refresh/verify Supabase session server-side and redirect non-admin users; continue to enforce RLS/RPC authorization independently. Re-check expired sessions and role revocation.
- **Acceptance:** unauthenticated/non-admin requests cannot obtain private data from page HTML, RSC payloads, APIs, Storage, or RPCs; expired and demoted sessions lose access; admin session refresh/logout works.

## Follow-up: admin authentication and connected admin data (2026-11-07)

The application source has since been updated for server-side admin gating. Treat the earlier admin-auth entries above as the audit's original finding; current source status is:

## Final Go/No-Go Decision

1. **Can Google crawl all important public pages? — UNVERIFIED for production.** The local candidate returned 200 for its main public pages and server-rendered a product page; no production request, Googlebot render, or Search Console inspection was performed.
2. **Are important pages returning correct HTTP status codes? — YES for tested local routes.** Tested public routes returned 200, invalid product/nonexistent routes 404, and sampled legacy URLs 308. Live/unpublished product behavior remains unverified; arbitrary product labels with a valid ID suffix still return 200.
3. **Are product metadata and canonical URLs correct? — NO overall.** The sampled local product metadata/canonical are correct, but site-wide canonicals are missing on most static routes, social tags inherit generic values, and Supabase-backed metadata has not been tested.
4. **Are product images properly optimized? — NO.** Raw `<img>` output is used; local optimizer request returned the unmodified source PNG; large image/video assets exist; uploaded absolute Storage URLs are malformed by current path handling.
5. **Is the site technically SEO-ready? — NO.** Status codes, XML sitemap, robots, server-rendered product body, and sampled Product/Breadcrumb JSON-LD work locally, but canonical/social/staging-indexing/image gaps remain and live data is unverified.
6. **Is the admin authentication secure? — LOCAL ALLOW/DENY VERIFIED; STAGING UNVERIFIED.** The dynamic `/admin` layout verifies JWT claims and the live profile role; Edge Middleware refreshes cookies, and database RLS remains independent. A temporary local admin session was admitted and blocked after its profile was demoted. Hosted session refresh, expiry, logout, and RLS verification remain outstanding; Next.js 16 deprecates the Edge `middleware.ts` convention.
7. **Can a non-admin user access sensitive data through Supabase or APIs? — UNVERIFIED.** Reviewed migrations restrict tables and admin RPCs, and no Next API route exists; direct role-matrix tests and deployed-policy verification are still required.
8. **Are admin CRUD operations functional and persistent? — PARTIAL; STAGING UNVERIFIED.** Products, categories, inventory, orders, and customer/analytics views use Supabase order/product data paths. Promotions and shared settings remain unconfigured; persistence was not exercised against staging.
9. **Is order and stock management secure? — UNVERIFIED end-to-end.** SQL design uses price re-reads, locks, transactionality, request idempotency, role checks, and cancellation restoration; no live database concurrency/authorization tests were run. Public order RPC abuse protection is missing.
10. **Is ENRM safe to deploy to production? — NO.** The migration candidate needs Supabase variable configuration, staging RLS/auth/checkout verification, image URL repair, staging index controls, and SEO/performance work before cutover.
